# 城市宠物友好线索采集

## 当前方式

当前使用 CUA 操作用户已登录的小红书可见页面，搜索城市加类别并打开详情页读取正文。不读取浏览器 Cookie 或存储，不调用私有接口。下文的独立 Playwright 采集器命令为旧流程记录，本次未运行。

遇到登录异常或访问限制时，`collector-state.json` 会将 `paused` 设为 `true`，采集器随后直接退出。先确认账号状态和平台提示，不要用换账号、换网络、换指纹或连续重试来绕过限制。

这是一套可断点继续的人工辅助采集流程，不保证平台长期可用，也不是全国全量数据。

## 数据及统计口径

- `content-*.json`：实际读到正文后整理的单篇记录，保留来源、页面显示时间、地点事实、内容转述及相关评论。
- `city-content.json`：按帖子 ID 合并去重；同一地点的不同帖子分别保留。
- `../generated/place-research.sqlite3`：`city_post_content` 为已保存内容；`collection_queue` 为采集队列。
- `pending-content-*.json` 及数据库 `city_pending_content`：已经读到正文、但地点尚未明确的摘要；不计入有效正文目标，也不进入小程序地点目录。地点确认并转为正式内容后，导入时自动从待核实表移出。
- `*-queue.json`：已发现的候选帖子及待处理状态。视频未读出地点和规则时，记作 `video_review_pending`，不计入正文数量。
- `city-targets.json`：依据 2025 年民政部区划数据整理的 297 个大陆地级市及直辖市首轮清单。
- `collection-progress.json`：依据实际内容生成全部目标城市统计，区分每城 3 篇的首轮达标与长期采集完成。
- `../../docs/research/city-post-content.md`：便于阅读的整理结果。

合并入库命令：

```sh
python3 server/place-research/save-content.py
```

重复导入不会增加相同帖子 ID 的数量。原先 `nationwide-posts.json` 的搜索索引不计为已读正文；旧上海原型的表也不并入本统计。

## 继续采集

1. 按城市分别检索咖啡、餐厅、商场、公园和酒店；每类保留多个独立来源，不以一篇代表整个城市。
2. 打开搜索卡片，读取正文及相关评论。搜索页与详情页分开保留，使用搜索页面已观察到的链接打开详情。
3. 只有月日或相对时间时保留原显示文字，发布日期留空，不推断年份。
4. 保存原链接及转述内容，不搬运整篇文章和图片。不把平台推荐词当成正文中的地点证据。
5. 后续评论若提到政策收紧、不同分店或不同体型，保留差异，不覆盖成统一“宠物友好”。
6. 每批导入进度。遇登录、验证码、账号异常或访问限制，写入持久暂停状态并关闭浏览器；不连续重试。

## 深度采集与断点队列

每城第一轮目标为 3 篇有效正文。优先覆盖尚未达标的城市，不再继续加深已超过 3 篇的城市；3 篇只是起步，不代表采完。只发现标题、读图待处理、视频待处理及无法定位的候选不拿来凑正文数。同一地点的不同作者分别保留，区分商家账号、个人到访和限制变化。

用户要求连续推进多个城市，不在每城完成后等待下一次“继续”。每城达到 3 篇后先保存进度，再在访问节奏和会话上限内继续下一座未达标城市；三篇是每城采集目标和入库批次，不是每次对话的停止条件。

独立浏览器的新增命令：

```json
{"op":"search","query":"武汉 宠物友好 咖啡","province":"湖北省","city":"武汉市","category":"咖啡馆"}
{"op":"results"}
{"op":"crawlSearch","query":"武汉 宠物友好 公园","province":"湖北省","city":"武汉市","category":"公园","maxScrolls":5}
{"op":"continueSearch","maxScrolls":5}
{"op":"batchOpen","city":"武汉市","limit":3}
{"op":"openNote","id":"搜索中实际发现的帖子ID"}
{"op":"mark","id":"帖子ID","status":"image_review_pending","reason":"正文信息在图片，尚未识别"}
```

`results`校验当前搜索页及关键词，按ID写入`browser-queue.json`，保留搜索来源；首页推荐不入队。`openNote`使用当前会话实际发现的链接并返回正文，不受搜索卡片虚拟化影响；跨会话需要重新搜索获取链接。带会话参数的URL只在内存，不写入数据文件。失败记录留在队列，不循环重试。

每批执行`save-content.py`，同步已保存状态、各城市与关键词正文数以及距阶段目标的数量。导入前校验必要字段，汇总JSON通过临时文件替换，避免不完整记录破坏文件。

用户取消了高德匹配，因此当前只保存作者提供的地址和地点信息，不补造地图坐标，也不将作者体验标成官方核验。

## 访问节奏与覆盖范围

- 搜索和详情页导航间至少间隔20秒；详情页逐篇读取，每批最多3篇，单会话最多10篇。已入库的帖子直接跳过。
- 逐个关键词人工发起查询，不再执行自动跨城市或跨类别扫量。单会话最多3次搜索、20次滚动。
- `crawlSearch` 默认5轮，单批最多10轮；批次上限不表示采完，`continueSearch` 仍受单会话总滚动上限约束。
- 初次搜索等待实际标题卡片出现，加载超时记录为 `load_timeout`，不误记为无结果。连续三轮无新卡片仅记录 `no_new_results_observed`。
- 搜索进度保存在 `search-progress.json`，候选队列持久化；浏览器重启仍须重新检索获得当前可访问链接，不能恢复原滚动位置。
- `detail_read_pending_review` 表示正文已读待整理，只有实际保存转述和地点字段并导入后才计入已入库正文。失败、待读图和待核实分别保留。
- 登录、账号异常或访问限制会将暂停状态写入 `collector-state.json` 并终止会话。旧的 `resume` 命令已停用。仅在账号状态确认正常、用户明确要求继续并重新评估采集方式后，才可手动解除暂停。无法保证取得平台全部帖子，也不会用搜索候选数冒充正文数量。

`crawlCity` 和 `crawlCities` 已停用。城市搜索批次结束不表示该城市已全量采完；正文整理和导入仍须单独执行。
